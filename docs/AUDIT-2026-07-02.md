## Executive summary

Overall the codebase is in solid shape — the `fix/audit-safety` branch's last commit (`713d1ac`) had already closed five real issues (fail-open auth, retention path traversal, inconsistent bool env parsing, session fixation, spoofable rate-limit IP), and this audit found no findings that re-open those. No **critical** findings surfaced. One **high**-severity correctness bug stands out: removing and re-adding a Pi-hole instance's env var permanently disables its scheduled backups with no error surfaced (`backup/services/discovery_service.py:124`). The next tier of **medium** findings clusters around three themes: (1) the retention-delete path-containment guard added in `713d1ac` was not extended to the download/restore read paths, which trust `record.file_path` unchecked; (2) the container runs as root with no `USER` directive, contradicting ADR-0001's documented (and marked "Implemented") non-root design; and (3) the shipped `docker-compose.yml` bakes a public placeholder `SECRET_KEY` default that silently defeats the app's own auto-generation mechanism. The **low**-severity tier is dominated by test-coverage gaps in the notification-provider layer (Discord/Slack/Telegram/Pushbullet/Home Assistant all lack direct unit tests) and several small duplication/dead-code quality items.

## Confirmed findings

### 1. [high] Re-added env var never reactivates a "removed" instance — scheduled backups silently never resume
- **Where**: `backup/services/discovery_service.py:124` (correctness)
- **Issue**: When a `PIHOLE_{PREFIX}_URL` env var disappears, the config is marked `connection_status='removed'`, `is_active=False`. If the same prefix is later restored, reconciliation skips the existing row (`if existing and not force`), and even the `--force` path only updates name/schedule/retention fields — never `is_active`/`connection_status`.
- **Failure scenario**: Operator temporarily removes or typos `PIHOLE_PRIMARY_URL`, restarts → instance marked removed/inactive. Operator restores the env var and restarts → `discover_instances` reports "Skipped (already exist)", the dashboard still shows Removed, and `runapscheduler.py` (which filters on `is_active=True`) never schedules that instance again. Only manual DB/admin surgery recovers it.
- **Suggested fix**: In the discovery reconciliation function, when a prefix is present in the environment and the existing row has `connection_status=='removed'`, reset `is_active=True`, `connection_status='unknown'`, `connection_error=''` regardless of the `force` flag. Add a remove-then-re-add regression test.
- **Verifier's evidence**: Confirmed via direct read of `discovery_service.py:105-154`, `runapscheduler.py:43,80`, and `retention_service.py:84`; no ADR documents this as accepted, and `test_discovery_service.py` has no remove-then-re-add test.

### 2. [medium] Session/CSRF cookies never marked Secure and no HTTPS hardening despite auth feature
- **Where**: `config/settings.py:176` (security)
- **Issue**: None of `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, `SECURE_PROXY_SSL_HEADER`, `SECURE_SSL_REDIRECT`, or HSTS settings are set anywhere. `backup/middleware/simple_auth.py` gates every page on the session's `authenticated` flag, so the session cookie is the actual auth token.
- **Failure scenario**: Operator enables `REQUIRE_AUTH` behind a TLS-terminating reverse proxy; gunicorn only ever sees plain HTTP and no `SESSION_COOKIE_SECURE`/`SECURE_PROXY_SSL_HEADER` is configured, so Django emits the session cookie without `Secure`. An attacker who can strip TLS or induce one plain-HTTP request captures the cookie and replays it for full UI access.
- **Suggested fix**: Add a production/HTTPS flag that, when set, applies `SESSION_COOKIE_SECURE=True`, `CSRF_COOKIE_SECURE=True`, and `SECURE_PROXY_SSL_HEADER` paired with the existing `TRUST_PROXY` setting.
- **Verifier's evidence**: `grep` across the file for `COOKIE|SECURE|HTTPS|SSL` returns zero hits. ADR-0001 claims "secure cookies" as implemented — the code doesn't match. Independently re-confirmed via a direct spot-check read.

### 3. [medium] delete_backup endpoint reports success even when the file could not be deleted
- **Where**: `backup/views.py:192` (correctness)
- **Issue**: `delete_backup_file_and_record()` returns `False` (keeping the DB record) when `unlink()` raises `OSError`. The view discards that return value and unconditionally responds `{"success": true}`.
- **Failure scenario**: `backups/` volume goes read-only (fs error, ro remount, NFS hiccup). Delete click → unlink fails → record kept → endpoint still reports success; the row vanishes from the UI then reappears on next load, while the user believes disk space was reclaimed.
- **Suggested fix**: `if not service.delete_backup(record): return JsonResponse({"success": False, "error": "..."}, status=500)`.
- **Verifier's evidence**: Confirmed via direct read of `backup_service.py:21-47,189-196` and `views.py:187-196`. Independently re-confirmed via spot-check.

### 4. [medium] Scheduler monitor gives up in a background subshell; container keeps running with backups permanently stopped
- **Where**: `entrypoint.sh:36` (correctness)
- **Issue**: After `MAX_RESTARTS=10` is exhausted, `monitor_scheduler`'s `return 1` is swallowed because it runs as a backgrounded subshell — nothing stops gunicorn or exits PID 1. `/health/` does return 503 and the compose healthcheck marks the container unhealthy, but `restart: unless-stopped` only acts on container exit, not health status, so the UI keeps serving while backups are dead and the app's own notification pipeline (which fires from scheduler jobs) stays silent.
- **Suggested fix**: On give-up, kill PID 1 / gunicorn so the container exits nonzero and the restart policy applies; optionally emit a notification before exiting.

### 5. [medium] Non-ZIP 200 response from Pi-hole is stored as a "success" backup
- **Where**: `backup/services/pihole_client.py:133` (correctness)
- **Issue**: A non-zip/non-octet-stream Content-Type only logs a warning; the body is still written to disk, checksummed, and recorded as `status='success'`. No ZIP magic-byte validation exists anywhere.
- **Failure scenario**: Pi-hole sits behind a proxy/auth portal that returns 200 `text/html` for the Teleporter endpoint (maintenance page, WAF block page). Every scheduled backup "succeeds"; retention rotates out real ZIPs; the corruption is only discovered when a restore is attempted and Pi-hole rejects the garbage upload.
- **Suggested fix**: Validate the ZIP magic bytes (`b'PK\x03\x04'`) after reading the body and raise a descriptive exception otherwise.

### 6. [medium] BACKUP_DIR containment guard covers delete only — download/restore trust record.file_path unchecked
- **Where**: `backup/services/backup_service.py:202` (quality)
- **Issue**: The path-containment guard added in `713d1ac` protects the delete path, but `get_backup_file()` (download) and `RestoreService.restore_backup()` (restore) both open `Path(record.file_path)` directly with no containment check — the exact threat model the delete guard's own docstring names ("a record whose file_path was tampered with via the admin, or an imported/legacy database"). `BackupRecordAdmin` leaves `file_path`/`checksum` editable.
- **Suggested fix**: Extract the `resolve()`+`relative_to(BACKUP_DIR)` check into a shared helper and use it on the download and restore read paths too; treat a blank checksum as a verification failure on restore; make `file_path`/`checksum` read-only in the admin.
- **Note**: Severity was corrected down from the finder's initial "high" to "medium" by the verifier — exploitation requires a Django staff/superuser account (none is created by the shipped setup) or direct sqlite write access.

### 7. [medium] Container runs as root — no USER directive, contradicting ADR-0001's "Implemented" non-root design
- **Where**: `Dockerfile:48` (quality, deployment)
- **Issue**: No `USER` directive exists anywhere in the Dockerfile. `docs/adr/0001` specifies `useradd -m -u 1000 appuser` + `USER appuser` and is marked "Implemented" in the ADR index — the implementation never adopted it.
- **Suggested fix**: Add the non-root user as ADR-0001 specifies, or if root is now the intended trade-off, amend the ADR and index so they stop asserting a security property that doesn't hold.

### 8. [medium] AJAX endpoints have drifted contracts — delete/restore return HTML 404 to a frontend that unconditionally parses JSON
- **Where**: `backup/views.py:187` (quality)
- **Issue**: `test_connection`/`create_backup` return JSON 404s; `delete_backup`/`restore_backup` use `get_object_or_404`, which raises `Http404` and returns Django's HTML 404 page. The frontend calls `response.json()` unconditionally.
- **Failure scenario**: A stale dashboard row (deleted by retention or a second tab) gets clicked → `response.json()` throws a `SyntaxError` → the user sees a garbled parse-error toast instead of "Backup not found."
- **Suggested fix**: Extract a shared `_json_get_or_404` helper for all four AJAX views.

### 9. [medium] Compose default SECRET_KEY is a publicly-known constant and silently disables auto-generation
- **Where**: `docker-compose.yml:13` (deployment)
- **Issue**: `SECRET_KEY=${SECRET_KEY:-change-me-in-production-use-long-random-string}` — since `get_or_create_secret_key()` returns any truthy env value, the persisted-random-key fallback can never execute under the shipped compose file. Every deployment that doesn't explicitly set `SECRET_KEY` runs with a literal string committed to the public repo.
- **Suggested fix**: Use `SECRET_KEY=${SECRET_KEY:-}` (empty string is falsy) so settings.py falls through to the persisted random key in the mounted `./data` volume.
- **Note**: Severity corrected down from the finder's "high" — the app uses default DB-backed sessions, not signed cookies, so a known `SECRET_KEY` cannot forge an authenticated session today; present-day impact is limited to forging the Django messages cookie.

### 10. [medium] Healthcheck detects scheduler exhaustion but nothing ever restarts the container
- **Where**: `docker-compose.yml:21` (deployment)
- **Issue**: Same root cause as finding #4 — the healthcheck correctly turns unhealthy, but `restart: unless-stopped` only triggers on container exit, not health status, and no autoheal exists in this stack.
- **Suggested fix**: Make the scheduler-exhausted case terminal at the process level (kill gunicorn/exit PID 1) so the restart policy actually applies; add `start_period` to the healthcheck.

### 11. [medium] pihole_backup_last_status tri-state and failure-path aggregation logic have zero assertions
- **Where**: `backup/services/metrics_service.py:141` (tests)
- **Issue**: No unit tests exist for `metrics_service.py`; a config with only-failed backups, zero backups, or duplicate-timestamp records is never asserted against the exposed `pihole_backup_last_status` gauge. A regression (e.g. swapping `latest_any_by_config` for `latest_success_by_config`) would pass the full suite while reporting healthy status during active failures.
- **Suggested fix**: Add `test_metrics_service.py` covering all-failed, no-records, and tie-break cases directly against `build_registry()`.

### 12. [medium] Home Assistant notification provider's dual auth-mode branching has zero test coverage
- **Where**: `backup/services/notifications/homeassistant.py:26` (tests)
- **Issue**: No test instantiates `HomeAssistantProvider`. The webhook-vs-Bearer-token branch, `validate_config()`'s either/or rule, and the 200/201 success check are all unverified.
- **Suggested fix**: Add provider-level tests mocking `requests.post` for both auth modes.

### 13. [medium] NotificationSettings event routing and provider loading from env are entirely untested
- **Where**: `backup/services/notifications/config.py:82` (tests)
- **Issue**: `should_notify()`'s substring event routing and `_load_providers()`'s five `NOTIFY_*_ENABLED` branches have zero coverage. A rename that drops the `"failed"` substring from an event value would silently disable failure alerts with all tests green.
- **Suggested fix**: Add tests using `monkeypatch.setenv` + `reload_notification_settings()` covering the truth table across all events/toggles.

### 14. [medium] Discord/Slack/Pushbullet provider send()/validate_config() have no direct tests
- **Where**: `backup/services/notifications/discord.py:46` (tests)
- **Issue**: None of the three providers are instantiated by any test. Discord's 204-only success check, Slack's `hooks.slack.com` prefix rule, and Pushbullet's header/status logic are all unverified — a normalization edit (e.g. Discord 204→200) would silently break real delivery with CI staying green.
- **Suggested fix**: Add per-provider unit tests mocking `requests.post` asserting exact success codes and payload shape.

### 15. [low] logout_view accepts GET and flushes the session (CSRF/prefetch logout)
- **Where**: `backup/views.py:306` (security) — no `@require_POST` guard; a cross-site GET or browser prefetch to `/logout/` silently ends the session. Nuisance denial-of-session, no data loss.

### 16. [low] Refresh job's remove_job/add_job window can silently drop a due backup run
- **Where**: `backup/management/commands/runapscheduler.py:87` (correctness) — `remove_job` then `add_job` are separate lock acquisitions; a scheduler tick landing in that gap misses the job entirely and pushes the next fire time to the following period with nothing logged.

### 17. [low] NotificationService lazy executor and module singleton are not thread-safe

## Methodology

- 41 Fable agents total: 5 finders (one per dimension: security, correctness, quality, deployment, tests) + 36 skeptic verifiers (one per raw finding), all on `model: 'fable'`. 0 agent failures, 0 empty results. ~1.58M subagent tokens, 534 tool calls, ~14 minutes wall clock.
- 36 raw findings reported, 6 refuted, 29 raw findings confirmed → deduplicated to the 29 entries above (one merge: the Dockerfile root-user finding was independently raised by both `quality` and `deployment`).
- No findings were capped/dropped (all dimensions stayed under the 15-per-dimension cap).
- **Caveat on this run's reliability, disclosed for transparency**: due to a scripting bug in how the audit workflow passed the repository path to agents, the header sentence of every agent's prompt literally read "auditing the repository at **undefined**" instead of naming this repo. Most agents self-corrected by searching for the repo-specific file paths named later in their prompt (e.g. `backup/services/discovery_service.py`) and correctly landed on `/media/cubxi/docker/projects/pihole-checkpoint`. However, **3 of the 6 refutations were corrupted by this bug**: the verifier agents for the `docker-compose.yml` SECRET_KEY finding, the `Dockerfile` root-user finding, and one of two `entrypoint.sh` cleanup findings instead inspected an unrelated, similarly-structured project (`nodered-backup`) and wrongly declared the citations "fabricated." In this run, all three underlying issues survived anyway because a second, independent dimension-finder had raised the same issue and its verifier correctly checked the right repo — but this was redundancy-driven luck, not a guarantee. The other 3 refutations (a deferred-dependency-upgrade finding and two duplicate reports of a dead-code branch in `simple_auth.py`) were legitimate, correctly-grounded refutations. Findings #1, #6, #7, #9, #23 above were spot-checked directly against the real repo in a separate verification pass to confirm the report's substance is sound despite this bug.
- Not covered: no runtime execution (no `pytest` run, no live app exercised) — all findings are static-analysis-derived; a CI-focused pass re-running the actual test suite would add confidence beyond this inventory-based read.
